# 账号定位独立视图（cockpit 十一期）

**日期:** 2026-08-15
**背景:** 十期把定位体系（人设定位卡 + 风格档案卡）做进了「设置」页，与 AI 服务配置、雷达配置、基线并列。用户实际体验前即指出问题：定位体系是**内容战略资产**（反复回看、随经营迭代），设置页是**配置项容器**（key/开关/阈值配一次不动），语义错位导致重要内容被埋没——同一个病此前已表现为「找不到生图配置」。用户明确要求：独立成侧栏**第一栏**。

## 0. 已确认决策

| 决策点 | 结论 |
|---|---|
| 位置 | 侧栏「工作台」组**第一项**（在灵感库选题之前）——定位是一切的前提 |
| 迁移范围 | 人设定位卡 + 风格档案卡迁至新视图；设置页只留配置三件（AI 服务配置 / 雷达配置 / 基线） |
| 体系报告 | 在新视图中放显眼位置（页面顶部区域），不再折叠在卡片深处 |
| 平台维度 | **本期不做**。用户已确认抖音与小红书的人群/侧重/写法不同，但先专攻抖音；等小红书接入时按「主定位 + 每平台侧写」扩展（侧写只在写稿层生效，不撕裂跨平台的雷达/选题），**不建多份独立档案**（避免人设分裂） |

## 1. 视图与导航

- `NavView` 新增 `'positioning'`；`WORKBENCH_NAV_ITEMS` 首位插入 `{ id: 'positioning', label: '账号定位', icon: <单色字形> }`。
- 新建 `src/components/cockpit/views/positioning.tsx`：
  1. **顶部：定位体系一页纸**——`systemSummary` 有内容时直接展示（markdown 原文 + 导出 .md）；为空时展示引导（「完成访谈与调研后，这里会生成你的定位一页纸」）。
  2. **中部：人设定位卡**（十期 `PersonaCard` 原样迁移，含 9 问访谈、痛点、商品服务、产品逻辑、市场调研）。
  3. **底部：风格档案卡**（`StyleProfileCard` 原样迁移）。
- 两张卡组件**不重写**，仅改挂载位置（`settings.tsx` 移除引用，`positioning.tsx` 引入）。
- 移动端 external-shell 的导航按 id 查找（六期已改），插入首项不会错位——实施时仍需核实。

## 2. 兼容与回退

- `view-routing.ts` 的 `resolveInitialView` 支持 `?view=positioning`；未知/旧地址行为不变。
- 旧地址 `?view=settings` 仍打开设置页（此时页内已无定位卡）——不做重定向，不做「已迁移」提示（YAGNI；用户是唯一使用者且本次改动由其发起）。
- 侧栏插入首项会让既有下标依赖失效——沿九期教训，全仓 grep 下标式访问 `WORKBENCH_NAV_ITEMS[n]` 并改为按 id 查找。

## 3. 不做（YAGNI）

平台维度的定位切换/侧写（见 §0，待小红书接入时）；定位档案版本历史与对比；体系报告的富文本渲染（markdown 原文展示即可，与十期一致）；设置页的「定位已迁移」跳转提示。

## 4. 风险

| 风险 | 对策 |
|---|---|
| 侧栏插入首项打乱下标依赖 | 全仓 grep 下标访问改按 id 查找（九期同类改动先例）；桌面/移动端各走查一次 |
| 两张卡迁移后状态/请求行为变化 | 组件不重写、props 不变，仅换挂载点；迁移后走查起草/保存/调研/报告四个动作各一次 |
| 用户正在体验流程中改动 UI | 改动集中在「卡片换个地方」，API 与数据零改动，不影响其进行中的建档数据 |

## 5. 实际实施结论（T1-T3 落地后回写，2026-08-15）

**(a) 侧栏图标复用既有字形 `◌`（T1）**：设计文档只写「单色字形」未指定具体符号。实施时读了 `Icon` 组件的既有字形表，没有语义精确对应「定位/靶心」的字符——排除了 `◉`（与既有选中态视觉冲突）、`◎`（已被雷达用作同心圆语义）、`✦`（已被 AI 服务配置卡用）、`⌕`（放大镜语义偏向搜索）。最终新起 `positioning` key 复用 `review` 键的圆环字符 `◌`，**未新增任何图标资源**，符合硬约束。语义偏弱是已知取舍，将来若引入图标库可单独替换，不影响功能。

**(b) 顺手修复 external-shell 遗留下标访问（T1）**：硬约束要求「全仓 grep 下标式导航访问并改按 id 查找」，grep 时发现 `external-shell.tsx` 里还有一处 `OVERVIEW_NAV_ITEMS[0]`——它不会被本次「插入 WORKBENCH 首项」直接打中（属另一个数组），但同属六期已修过一次的同类隐患，按约束字面无条件修掉，改为 `.find(item => item.id === 'pipeline')!`。

**(c) 新建本仓首个 component 级测试（T1）**：`tests/components/cockpit/sidebar.test.ts`。简报的验收断言（`WORKBENCH_NAV_ITEMS[0].id === 'positioning'` 且长度 +1）原本只是口头验收项，实施时确认 vitest 在本仓 node 环境下可直接 import `.tsx` 拿到导出的常量（不渲染组件、不需要 jsdom），成本极低，遂落成可回归用例。这是本仓第一个 `tests/components/` 下的测试文件，后续同类「导出常量断言」可循此先例，但**不等于**本仓具备组件渲染测试能力（仍无 jsdom/@testing-library）。

**(d) 体系报告区自取数造成一次重复请求（T2，刻意取舍）**：新视图顶部的体系报告区自行 `GET /api/v1/persona/profile` 取 `systemSummary`，而其下方的 `PersonaCard` 内部也会取同一份数据——同一页面两次相同 GET。不做跨组件状态提升/context 共享，理由：两卡本期硬约束是「零重写」，为省一次 GET 引入状态提升就必须改卡片本体，代价远大于收益；单用户本地应用，一次多余 GET 无实际影响。

**(e) 报告区无独立错误态（T2，可接受简化）**：`fetch` 失败被 `try/catch` 静默吞掉、`systemSummary` 保持空串，渲染落到「完成访谈与调研后，这里会生成你的定位一页纸」这条引导文案——即网络失败与「真的还没生成过报告」共享同一 UI 表述。设计文档只要求两态（有内容/引导），未要求第三态，故不视为缺陷，仅记录。

**(f) 破坏性动作未做真实点击走查（T2，验证降级及其理由）**：走查清单里「市场调研」「生成定位体系」「删除风格样本」三个动作**没有真实点击**。原因不是偷懒，而是这三个动作都会**立即不可逆地覆盖或删除用户正在建立的真实档案数据**（1180 字体系报告、市场调研结果、2 条定稿样本），与本期最硬的约束「零 API/零数据改动（用户正在真实建档）」直接冲突——约束优先级判定为：保护用户真实数据 > 补一次实测。替代验证：① `git diff` 客观证明 `persona-card.tsx`/`style-profile-card.tsx` 两文件零字节改动、且两卡不接收 props，React 子组件行为不随父组件身份变化，挂载点变更在原理上不可能影响其内部逻辑；② 这三条链路本身已在十期收尾（`positioning-system` task-7）用真实 DeepSeek+Tavily key 做过完整 E2E 验证，本期不是重新发明链路。「保存」链路做了真实写入-核对-恢复往返测试（无 LLM 成本、可安全回滚）。任务审查者独立复核后判定该降级对本任务范围充分。

**(g) 浏览器扩展不可用，改用 Playwright 直连（T2）**：Chrome MCP 扩展本会话全程超时/无法确定 tab，判定不可用。走查改用 Playwright 直连本机已缓存的 Chromium 做真实浏览器交互（`?view=positioning` 直达、侧栏点击、移动端首项、设置页只剩三卡、明暗主题、保存往返），**比预案的「API 级验证 + 代码走读」更强一档**。走查中观察到一次未复现的 404 控制台告警，判断为 dev server 增量编译期间的瞬时资源加载异常（`positioning.tsx` 未引用任何新资源），如实记录不掩盖。

**(h) README 由 T2 提前完成（任务边界交叉，记录在案）**：计划把 README 更新划给 T3，T2 顺手做了（内容准确、与实际改动一致，符合全局文档维护规则）。T3 执行时核对 README 现状确认已完整，未重复改动，只补本节 spec 回写与最终验证。属无害的边界交叉，记录以免后续读者困惑。

**(i) 平台侧写待办再确认（跨期）**：用户已明确「抖音与小红书的侧重点、用户群体、文章风格写法完全不一样」，但当前先专攻抖音，故本期档案仍是账号级唯一一份（实际承载的就是抖音定位）。将来接入小红书时，正确形态是**主定位 + 每平台侧写**：主定位（受众/痛点/商品服务/产品逻辑）跨平台共享保证人设一致，侧写（侧重哪个痛点、偏哪个支柱、表达形态差异）**只在写稿层生效**，不进雷达/选题——因为雷达池的选题没有平台属性（采纳后才决定做成哪个平台），若定位分平台会立刻面临「雷达该用哪份定位打分」的架构裂缝，要么退化成只在写稿生效（价值薄），要么雷达也得分平台（成本翻倍）。**明确不建多份独立档案**（人设分裂风险，且违背八期建立人设档案的一致性初衷）。表达形态的平台差异，现状已由「风格样本按平台独立积累」+ 九期平台差异化流水线部分覆盖。
