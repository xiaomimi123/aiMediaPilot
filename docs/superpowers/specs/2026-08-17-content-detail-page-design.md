# 抖音内容详情页改造（十四期收窄版）

**日期:** 2026-08-17
**背景:** 用户反馈「不知道该怎么用前端」——具体定位到：抽屉里 7 个标签页（概览/大纲/脚本/录制/剪辑/发布/复盘）是一排平级按钮，没有"现在到哪了/下一步点哪个"的提示；而且每次打开抽屉都硬编码停在「概览」，跟内容实际所在阶段无关（`Cockpit.tsx:528` `useState<ContentDrawerTab>("overview")`）。另外，录制/剪辑阶段只有空白备注框+打勾清单，用户不知道该写什么内容。侧栏 9 项结构、看板列=阶段的组织方式本身用户认可（每天都看），不在本次改造范围内。

本次是十四期「任务式主流程」的收窄落地：不做全新的"做一条内容"引导流程，而是把现有看板→抽屉这条路径里最具体的卡点修掉。

## 0. 已确认决策

| 决策点 | 结论 |
|---|---|
| 改动范围 | 只改"点看板卡片之后发生什么"，看板本身（列=阶段、拖拽换阶段）**不动**；侧栏 9 项结构**不动** |
| 承载方式 | 取消右拉抽屉，改为跳转到独立整页（真实 Next.js 路由，有自己的 URL，可刷新/可分享），不是 URL 参数糊在单页应用里 |
| 页面内导航 | 连线步骤条（已完成绿勾 / 当前金色放大 / 未到灰圈），打开页面自动定位到内容当前所在阶段；其余节点仍可自由点击，**不锁顺序** |
| 录制/剪辑指导 | 从已生成的六幕脚本（`output.script.acts`）铺开成逐幕对照清单（台词+配图建议+打勾）；没有脚本或脚本非六幕形态的内容，退回原有空白备注框，**零迁移** |
| 数据加载方式 | 新页面复用现有整仓库一次性加载机制（`loadWorkspace()`），不新建单条内容的读写接口——详见 §2 技术决策说明 |

## 1. 现状问题（已核实）

- `Cockpit.tsx:528`：`selectedTab` 硬编码初始值 `"overview"`，与 `item.stage` 无关，每次开抽屉都要用户自己找该点哪个标签。
- `content-drawer.tsx` 的 `<div className="drawer-tabs">` 只是一排 `<button>`，视觉上完全平权，没有顺序/状态提示。
- `platform-stages.ts` 已经有 `stageFlowFor(platform)` 给出每个平台的阶段顺序（抖音等 6 步：大纲/脚本/录制/剪辑/发布/复盘；小红书 3 步：大纲/文案/发布），本次直接复用，不新造状态机。
- 录制/剪辑阶段字段（`item.recordingNotes` / `item.editingNotes`）是纯文本框，跟已经生成的六幕脚本内容（每幕的 `narration`/`visual`/`note`/`beats`）完全脱节——脚本里明明有台词和配图建议，用户还是要对着空白框自己想。

## 2. 新整页：路由与数据加载

**路由：** `src/app/content/detail/[id]/page.tsx`（服务端组件，`id` = `ContentItem.id`）。与已有的 `/content/script/[id]`（旧的、只读的 `ScriptDraft` 详情页，键是 `ScriptDraft.id`，本次不动）分属不同命名空间，不冲突。

**技术决策说明（为什么不新建单条内容的读写接口）：** 现在 `WorkspaceState` 是"整仓库一次性加载、客户端持有全部状态、所有编辑防抖后整体 PUT 回服务端（带 `rev` 乐观锁）"的架构（`src/app/api/v1/cockpit/workspace/route.ts` 只有 `GET`/`PUT` 两个方法，没有任何单条内容的接口）。给这一条内容单独开一对读写接口，意味着要在现有"整体读写"之外并行维护第二套持久化路径，改动面和出错面都远大于导航结构调整本身该有的规模。新整页改用真实路由**只解决"有没有自己的 URL"这一件事**，数据加载与所有编辑操作仍然复用现有的 `loadWorkspace()` + 整体状态 + 防抖 PUT 机制（把 `Cockpit.tsx` 里这部分状态管理逻辑抽成一个共享 hook，供 `Cockpit.tsx` 和新页面共同使用）。刷新页面时行为与现在刷新整个 cockpit 单页一致：重新拉一次全量 workspace，本地过滤出这一条。

**关闭/返回：** 页面顶部「← 返回看板」链接回对应的平台看板页（`/?view=platform-<platform>`），不做浏览器历史特殊处理。

## 3. 步骤条

复用 `platform-stages.ts` 的 `stageFlowFor(item.platform)` 得到该平台的阶段顺序（如抖音：`topic/script/recording/editing/publishing/review`）。步骤条节点 = 这个数组，每个节点：

- 排在 `item.stage` 之前 → 完成态（绿色 ✓）
- 等于 `item.stage` → 当前态（金色，放大，光晕）
- 排在之后 → 未到态（灰色空心圆）

节点之间用连线连接，已完成段落绿色、当前段落金色、未到段落灰色（视觉参考见头脑风暴阶段浏览器 mockup，方案 A "连线步骤条"）。「概览」作为不参与编号的独立标签放在步骤条最左侧（复用现有 `overview` tab 内容：`StageStatusPanel` + 全局字段编辑 + 下一步动作卡）。

页面打开时，默认展示的内容区 = 步骤条当前态对应的那个阶段（不再默认停在概览）。点击任意节点（含概览）切换展示区，不做順序锁定、不禁用未到达的节点——真实创作流程不总是线性的（比如提前想好发布文案）。

## 4. 录制 / 剪辑阶段：从六幕脚本铺开指导清单

**判别入口：** 复用十三期 `isSixActScript`（`src/lib/script/six-act.ts`）判断这条内容关联的脚本是否为六幕形态。

**六幕稿命中时：** 录制阶段和剪辑阶段的内容区渲染六幕逐幕清单，每幕一张卡：

- 幕标签（`ACT_LABELS[act]`）+ 建议时长（`targetSec`）
- 台词（`narration`）——录制阶段对着念/演的内容
- 配图建议（`visual`）——剪辑阶段该配什么画面
- 创作备注（`note`）
- 关键词（`beats`，chip 展示）
- 逐幕打勾"这一幕录完了 / 剪完了"（新字段，见 §6）

**非六幕稿或没有脚本时：** 完全保留现有渲染——`item.recordingNotes`/`item.editingNotes` 空白备注框 + 现有打勾清单，不做任何改动。判别逻辑与六幕改造十三期沿用的原则一致：**旧内容零迁移，每一处消费点显式分岔**。

## 5. 发布 / 复盘阶段

不改动现有字段与交互（发布状态、发布正文、复盘评分/分析/规则沉淀等），只是承载它们的容器从抽屉 tab 变成整页步骤条节点。

## 6. 数据结构改动

`ContentItem`（`src/lib/cockpit/model.ts`）新增可选字段，用于记录逐幕录制/剪辑打勾状态（不影响旧数据，缺省即未打勾）：

```ts
recordingActProgress?: Record<ActKey, boolean>; // 六幕稿专用，键=act，值=是否已录
editingActProgress?: Record<ActKey, boolean>;   // 六幕稿专用，键=act，值=是否已剪
```

非六幕稿内容不产生这两个字段，`recordingNotes`/`editingNotes` 字段与现有打勾清单渲染逻辑完全不变。

## 7. YAGNI（不做）

- 不新建单条内容的读写 API（见 §2 决策说明）。
- 不锁定步骤条顺序、不禁用未到达节点。
- 不改侧栏 9 项结构、不改看板列/拖拽逻辑。
- 不改发布/复盘阶段的字段与交互。
- 不涉及本次会话讨论过的「AI 视频生产引擎」（选题→文案→SRT→预览确认→导出）——那是完全独立的十五期项目，技术验证结论见项目记忆 `project-broll-engine-findings`，需要单独立项。
- 不做 talking-head 模式的 ASR 对齐、不接 `erduo-broll-loop-engineering` 或任何视频渲染引擎。

## 8. 风险

| 风险 | 对策 |
|---|---|
| 抽出共享 hook 时不小心改动 `Cockpit.tsx` 现有的防抖/乐观锁/`refreshWorkspace` 逻辑，引入回归 | 抽取时逐行对照现有实现，新旧调用点各写一条集成测试断言状态变化/自动保存时机不变 |
| 新路由与旧 `/content/script/[id]` 命名或语义混淆 | 页面顶部明确文案区分（"内容详情"而非"脚本详情"），两者互不跳转 |
| 六幕清单的逐幕打勾字段（`recordingActProgress`/`editingActProgress`）与旧 `recordingNotes`/`editingNotes` 并存，未来某处遗漏读取新字段 | 打勾状态只影响这一处 UI 展示（清单勾选），不参与阶段推进判定（推进阶段仍由用户手动切换 `item.stage`），影响面小 |
| 步骤条"自动定位当前阶段"与"点击任意节点自由跳转"两者共存，用户可能困惑"到底跳没跳阶段" | 步骤条本身只是**展示导航**，不等同于推进阶段；阶段推进仍然是看板拖拽或抽屉/整页里已有的"全局当前阶段"下拉，步骤条节点的绿/金/灰只反映 `item.stage`，不由点击步骤条本身触发变更 |
